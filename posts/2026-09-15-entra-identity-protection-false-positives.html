Entra Identity Protection False Positives: When You Cannot Even Dismiss a Risky User

September 2026 • By Philipp Schmidt
Entra IDSecurityIdentity ProtectionMonitoring

A security tool that flags real risk and also floods the queue with false positives eventually gets the same response either way: admins stop reading it closely.

That is the practical failure mode with Identity Protection — risky user detections that turn out to be false positives, and then a recurring bug where the dismiss action itself does not reliably clear the flag, leaving a resolved false positive sitting in the queue as if it were still open.

In short

Identity Protection's value depends on admins trusting it, and a dismiss action that does not reliably persist undermines that structurally. Verify the risk state via Graph after dismissing rather than assuming the click worked. Leaked Credentials is a dataset match, not a confirmed breach — investigate before escalating. And P1 tenants have no risk detection at all; the answer there is Conditional Access on device, location and MFA signals, not a scaled-down risk score.

Why the dismiss button matters more than it sounds

Dismissing a risky user is not cosmetic. It is how Entra ID learns which detections were wrong, and a dismiss that intermittently fails to persist means the same false positive can resurface or sit unresolved indefinitely, muddying any attempt to separate real open risk from noise.

If dismiss is not behaving reliably in your tenant, do not assume the risk state cleared just because you clicked it. Check directly via /identityProtection/riskyUsers/{id} in Microsoft Graph, or the risky users list in the admin center, and confirm the state actually moved to dismissed or remediated rather than persisting as at risk.

Leaked Credentials without independent confirmation

The Leaked Credentials detection flags sign-ins where a username and password pair appears to match known-compromised credential dumps. Valuable, but it is a match against a dataset — not a live breach confirmation. A credential can appear leaked based on data that is old, based on a password the user has since changed, or on a partial match that is less clean than the alert implies. Treating every one as a live compromise burns investigation time on stale matches.

The detection is also effectively all-or-nothing at tenant level: disabling it to reduce noise means losing it entirely, not tuning sensitivity. That is a real trade-off, not a setting to flip casually.

A reasonable triage order: confirm whether the flagged password is still in use (a forced reset resolves this regardless of whether the match was accurate), check recent sign-in activity for anything corroborating compromise, and escalate to full incident response only if either turns up something real.

P1 versus P2: what risk detection you actually have

Identity Protection's risk detection and risk-based Conditional Access require Entra ID P2 or Microsoft 365 E5. P1 tenants do not get risk-based sign-in or user-risk policies at all — there is no scaled-down version, it is simply absent. That matters because "Identity Protection" gets used loosely, and a P1 admin reading about risky user detection may not realise the feature is unavailable regardless of configuration effort. On P1, build Conditional Access on the signals you do have — device compliance, location, MFA state — since there is no risk score to build a policy on. See the Identity pillar for how those fit together.

Reducing false positives without losing signal

  • Exclude known-safe network ranges — office IPs, established VPN egress — from location-based risk via named locations, so travel-pattern false positives from expected infrastructure drop out
  • Require step-up authentication rather than a hard block at medium risk, reserving blocks for high risk. This reduces the cost of a false positive from a lockout to an extra prompt
  • Review risk policy scope regularly — a policy scoped too broadly generates volume a narrower one would not

Alert triage for MSPs across many tenants

At fifty-plus tenants, per-tenant manual review does not hold up, which is why the honest answer in MSP circles is often "we do not investigate most alerts." The workable approach is a centralised layer surfacing only high-risk, high-confidence detections across all managed tenants into one queue, with medium and low risk handled by automated remediation — forced reset, step-up MFA — rather than manual review. Building it needs either a PSA/RMM integration pulling the Graph identityProtection endpoints across tenants, or a multi-tenant layer plus a scripted rollup. Either way, the answer to "how do I review this manually across fifty tenants" is that you do not; you triage by policy.

Bottom line

Identity Protection is only as useful as the trust admins place in it. Verify dismissals actually persist, treat Leaked Credentials as a lead rather than a verdict, and if you are on P1, stop looking for a reduced version of risk detection that does not exist.

Glossary

Identity Protection
Entra ID P2 risk engine that scores users and sign-ins for compromise likelihood and can feed that risk into Conditional Access.
Risky user
A user Entra ID has flagged as likely compromised. The state persists until remediated or dismissed — and the dismiss action does not always stick.
Leaked Credentials
A detection raised when a credential pair matches a known-compromised dataset. A lead requiring investigation, not a confirmed live breach.
Named location
A defined IP range or country in Entra ID used to exclude known-safe infrastructure from location-based risk signals.
Step-up authentication
Requiring an additional, stronger authentication factor in response to elevated risk, instead of blocking the sign-in outright.

Frequently Asked Questions

Why can I not dismiss Risky Users in Identity Protection?

There is a recurring issue where the dismiss action does not reliably persist. After dismissing, verify the actual risk state via Microsoft Graph (/identityProtection/riskyUsers/{id}) or the admin center rather than assuming the click cleared it.

Are Entra ID Leaked Credentials alerts always real?

The detection matches against known-compromised credential datasets, which can include stale matches or passwords already changed. Worth investigating, not automatically treating as active compromise — confirm current password use and recent sign-in activity before escalating.

How do I reduce false positives in Identity Protection without losing coverage?

Exclude known-safe network ranges from location-based risk via named locations, use step-up authentication instead of hard blocks at medium risk, and review risk policy scope regularly rather than leaving it broad.

Do SMBs really need Entra ID P2 for risk detection?

Risk-based sign-in and user-risk Conditional Access require P2 — there is no reduced version on P1. P1 tenants can still build meaningful Conditional Access on device, location and MFA signals without a risk score.

How should MSPs triage Identity Protection alerts across dozens of tenants?

Manual per-tenant review does not scale past a handful. A centralised queue surfacing only high-confidence, high-risk detections, combined with automated remediation for medium and low risk, is the realistic approach.
